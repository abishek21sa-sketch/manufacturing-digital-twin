# Technical Methods — V1.0

This document is the engineering-methods reference for the V1.0 release. It is deliberately explicit about model role, units, assumptions, validation and the boundary between benchmark/synthetic evidence and external plant validation.

# A. ARTIFICIAL INTELLIGENCE

## A1. Lateness-risk classification

**Task.** Estimate job lateness risk under benchmark-derived production scenarios.

**Features.** Release/due allowance, total/mean/max operation time, critical-ratio style allowance, workload on the static constraint, constraint-work share, system/mean machine load and due tightness (`src/mdt/ai/scenarios.py`).

**Target.** Binary late/not-late outcome under the deterministic scenario schedule.

**Model / training.** Standardized logistic regression selected against a class-prior baseline and Gradient Boosting challenger. Scenario IDs are group-split so jobs from the same generated factory scenario cannot leak across partitions.

**Metrics.** ROC-AUC, PR-AUC, F1, Brier score and 10-bin ECE. Evidence: `docs/evidence/AI_VALIDATION.json`.

**Uncertainty.** Output is a model probability under the synthetic data-generating distribution; Brier/ECE quantify calibration on the synthetic holdout only.

**Decision use.** `risk_score` becomes a tardiness penalty in the MILP. Local log-odds feature contributions are exposed for explanation and are explicitly non-causal.

## A2. Remaining / cycle-time regression

**Task.** Estimate job flow/cycle time for a planning scenario.

**Features.** Job work/routing profile and scenario production-load features generated by `src/mdt/ai/operational.py`.

**Target.** Simulated job flow time.

**Models.** Standardized Ridge versus HistGradientBoostingRegressor; the production candidate is selected by untouched test MAE rather than model sophistication.

**Baseline.** Nominal touch time (sum of operation processing times), which ignores waiting/interaction.

**Metrics.** MAE, RMSE and R²; grouped scenario split. Packaged closure evidence currently reports production MAE materially below the touch-time baseline. Exact values are in `docs/evidence/OPERATIONAL_AI_VALIDATION.json`.

**Decision use.** Predicted cycle time appears beside lateness risk in the decision contract so planners see expected flow consequence, not just a binary risk label.

## A3. Future bottleneck prediction

**Task.** Predict which machine is most likely to become the dynamic pressure constraint under a future variability/reliability scenario.

**Features per machine.** Nominal load share, operation-count share, mean operation time, assumed availability, process CV and static-constraint indicator.

**Target.** Machine with maximum simulated dynamic pressure index (productive utilization + downtime fraction) for each scenario.

**Models.** Standardized multinomial/logistic classifier versus histogram Gradient Boosting challenger.

**Baseline.** Static workload constraint from deterministic factory physics.

**Validation.** Grouped scenario holdout; top-1 machine accuracy plus multiclass ranking metrics. Evidence is in `OPERATIONAL_AI_VALIDATION.json`.

**Decision use.** Probabilities allocate stronger robust processing buffers to likely constraint machines and select a default machine to stress when the operator gives no override.

## A4. Operational anomaly detection

**Task.** Flag machine-state patterns inconsistent with the generated normal operating envelope.

**Features.** Completed-work ratio, mean cycle ratio, downtime fraction, ready-queue fraction, busy indicator and nominal load share.

**Model.** Isolation Forest trained only on synthetic normal envelopes.

**Evaluation.** Separate synthetic anomaly set with injected cycle-time, queue and downtime distortions. Baseline is a simple downtime-only threshold. ROC-AUC and PR-AUC are reported.

**Output semantics.** The anomaly index is **not a probability**. A flag triggers human review / stress-analysis attention; it never autonomously changes plant state.

## A5. Gemini engineering interrogation

**Task.** Convert natural-language requests into typed bounded scenario parameters and explain already-computed evidence.

**Provider.** Google Gemini through the Google GenAI SDK, configured exclusively through local environment variables.

**Validation.** Deterministic fake-transport tests verify structured schemas; Phase 4 Windows acceptance validated a real key/provider path.

**Decision use.** Gemini sits above the deterministic tool chain. It cannot invent solver values, factory arithmetic or simulation results.

# B. INDUSTRIAL ENGINEERING

## B1. Little's Law and flow conservation

`L = λW`

- `L`: average WIP [jobs]
- `λ`: throughput [jobs / time]
- `W`: mean flow time [time]

Implemented in `src/mdt/ie/factory_physics.py`; the DES independently computes both sides of the relationship. Mathematical tests verify exact reference cases and simulated closure.

## B2. Utilization, capacity and takt

`ρ = λ / μ` for queue utilization when a service-rate interpretation is valid.

`Capacity = Available Time / Effective Cycle Time`

`Takt = Available Production Time / Customer Demand`

`capacity_plan(...)` computes per-machine workload, effective available horizon, load ratio and capacity gap. Takt is only returned when demand is explicitly supplied; the API intentionally labels it unavailable when customer-demand signals are absent.

## B3. Theory of Constraints and dynamic bottlenecks

Static constraint:

`Load_m = Σ_o p_o`, for operations assigned to machine `m`.

Dynamic pressure:

`Pressure_m = ProductiveUtilization_m + DowntimeFraction_m`.

The static result drives the initial DBR drum; the dynamic measure and AI bottleneck predictor can disagree under failures/variability. This distinction prevents a static workload rank from being presented as immutable future truth.

## B4. Drum-Buffer-Rope

`drum_buffer_rope_plan(...)` sequences jobs by due-date priority on the identified constraint, computes work before the constraint, drum start/finish, and rope release time:

`RopeRelease_j = max(OriginalRelease_j, DrumStart_j - UpstreamWork_j - Buffer)`.

The result is an executable release-control plan, not a label on a dashboard.

## B5. CONWIP

A shop-floor job is admitted only when:

`Current WIP < WIP Card Limit`.

The DES maintains a pending-release queue and admits jobs as cards free on completion. The PLANNED policy preserves machine sequence among **admitted** jobs so a CONWIP-held job cannot deadlock the shop. A regression test specifically covers this interaction.

## B6. Lean / JIT / Process Cycle Efficiency

`PCE = Value-Added Time / Total Lead Time`

`Latest JIT Release = Due Time - Remaining Touch Time - Explicit Safety Buffer` (floored at zero).

These calculations are implemented as engineering measures/control inputs. The project does not claim observed waste removal without real value-stream data.

## B7. OEE and reliability

`OEE = Availability × Performance × Quality`

`Availability = MTBF / (MTBF + MTTR)`.

OEE is computed only if all three input fractions are supplied; the live IE endpoint explicitly marks OEE unavailable when quality and ideal-cycle signals are missing. Reliability assumptions feed both capacity interpretation and the DES failure/repair process.

## B8. Kingman's approximation

`Wq ≈ [ρ/(1-ρ)] × [(Ca² + Cs²)/2] × E[S]`, for `ρ < 1`.

Implementation rejects unstable/incoherent parameterizations and is validated against reference cases.

## B9. SPC — Individuals / Moving Range

For observed values `X_i`, moving ranges are `MR_i = |X_i-X_{i-1}|`.

`σ̂ = MRbar / d2`, with `d2 = 1.128` for a moving range of 2.

Individuals limits:

`UCL = Xbar + 3σ̂`

`LCL = Xbar - 3σ̂`.

`individuals_mr(...)` returns center line, moving-range mean, control limits and out-of-control indices. Closure tests include an injected excursion. Control signals are not called defects or causal root causes.

## B10. DOE / sensitivity

`two_level_factorial_effects(...)` accepts coded `-1/+1` factors, calculates main and pairwise interaction contrasts, and returns engineering effects. Closure diagnostics execute an 8-run `2^3` experiment over process CV, MTBF and MTTR with total tardiness as response.

# C. OPERATIONS RESEARCH

## C1. Synchronized residual scheduling model

Before any operation-level optimization, `planning_state_from_twin(...)` converts `TwinSnapshot` into a residual decision problem:

- completed operations are removed;
- running operations are frozen/projected from observed starts;
- current twin time is the scheduling clock;
- machine availability is carried forward;
- a DOWN machine requires an explicit recovery timestamp;
- the state gets a deterministic `twin_state_id`.

This is the critical Digital-Twin-first contract.

## C2. Nominal finite-capacity job-shop MILP

**Variables**

- `S_o ≥ 0`: operation start time;
- `Y_ij ∈ {0,1}`: disjunctive order for same-machine operation pair;
- `T_j ≥ 0`: job tardiness;
- `Cmax ≥ 0`: makespan.

**Objective**

`min α Cmax + Σ_j w_j[β + γ r_j]T_j`,

where `r_j` is AI lateness risk.

**Constraints**

- job precedence;
- job release / current-twin readiness;
- machine-ready time;
- pairwise machine non-overlap;
- tardiness definition;
- makespan bounds;
- binary/continuous domains.

**Solvers.** Gurobi primary on Windows; separately coded SciPy/HiGHS implementation. Solver status, objective, best bound, gap and runtime are retained.

**Independent verification.** A solver-independent validator checks processing duration, machine assignment, releases, precedence and illegal overlap. FT06 Gurobi/HiGHS benchmark agreement is a separate regression.

## C3. Formal box-robust scheduling

Processing time is protected with bounded machine-specific relative inflation:

`p'_o = p_o(1 + δ_m)`.

The robust model solves the same finite-capacity problem against `p'`. Bottleneck predictions can allocate larger `δ_m` to higher-risk machines. Results explicitly disclose the uncertainty set and are feasibility checked under robust durations.

This is a robust counterpart—not a claim of probabilistic coverage.

## C4. Multi-objective / Pareto scheduling

Multiple scalarizations of makespan, aggregate tardiness and risk-weighted tardiness are solved; dominated duplicates are removed in all three objective dimensions. Each retained point records objective weights, makespan, total tardiness, risk-weighted tardiness, solver backend/status, objective value and whether optimality was actually proven.

A solver may reach `TIME_LIMIT` after finding a complete incumbent. Such a schedule is retained only if the solver-independent feasibility validator confirms all operation, precedence and machine-capacity constraints; it remains labeled `TIME_LIMIT` with `optimality_proven=false`. The decision path uses a bounded fast pass and, if a slower platform returns no incumbent, retries a balanced scalarization with the caller's full solve budget. The resulting set is therefore a validated nondominated candidate frontier, while global Pareto-optimality is claimed only for points whose scalarized solve is `OPTIMAL`.

This exposes trade-offs without conflating a feasible incumbent with an optimality certificate.

## C5. Scenario-based stochastic CVaR policy-selection MILP

After common-random-number Monte Carlo creates per-policy tardiness losses `L_{p,s}`, the system solves a distinct stochastic optimization model.

**Variables**

- `x_p ∈ {0,1}`: choose one candidate policy;
- `η ≥ 0`: CVaR threshold (VaR surrogate);
- `u_s ≥ 0`: scenario excess loss.

**Objective**

`min Σ_p x_p E[L_p] + λ[η + 1/((1-α)N) Σ_s u_s]`.

**Constraints**

`Σ_p x_p = 1`

`u_s ≥ Σ_p L_{p,s}x_p - η` for every scenario `s`.

The packaged model uses `α = 0.95` by default and the configured risk aversion `λ`.

**Solver.** SciPy/HiGHS MILP.

**Independent oracle.** Because the number of candidate policies is small, the exact objective of every policy is enumerated. An optimal MILP result must agree with enumeration within tolerance or the run fails.

This is distinct from the operation-level robust MILP and from descriptive Monte Carlo ranking.

## C6. Simulation optimization

Candidate policies include SPT, EDD, nominal AI-risk schedule and box-robust schedule. They receive common seed sets under the same processing/failure assumptions. The scenario loss matrix becomes input to the stochastic policy MILP above.

## C7. Why no standalone network-flow or CP model

The current manufacturing benchmark has **fixed routings**. There is no route-selection/material-network decision to optimize independently; inventing a network-flow layer would add terminology without a real decision variable. Likewise, a CP formulation would duplicate the already independently verified disjunctive scheduling decision unless it demonstrates a scale/performance benefit. Both are therefore documented as justified non-separate capabilities rather than falsely claimed as implemented.

# D. DECISION CONTRACT AND AUDITABILITY

Every synchronized recovery run includes:

- deterministic run ID and twin-state ID;
- evidence labels for observed/predicted/optimized/simulated quantities;
- AI estimates and explanations;
- baseline, nominal and robust decisions;
- solver evidence and independent violations;
- Pareto trade-offs;
- modeled expected impact;
- uncertainty and assumptions;
- trade-offs / limitations;
- `human_review_required` and disposition (`pending`, `approved`, `rejected`, `deferred`).

Decision runs are persisted to SQLite with model version, solver backend, data version and request/result payload. This is an audit trail, not a production MES transaction log.

# E. VALIDATION BOUNDARY

**Validated here:** benchmark parsing, state replay, mathematical reference equations, AI synthetic holdouts, solver feasibility/oracle checks, deterministic DES bridge, stochastic simulation invariants, robust/stochastic decision logic and Windows runtime behavior.

**External validation pending:** real plant calibration, historical predictive validation, live MES/ERP/IIoT integration, actual OEE/SPC/demand signals, site acceptance and realized operational benefits.

### Solver result quality contract

Scheduling termination state and physical feasibility are treated separately. `ScheduleAssessment` is the repository-wide oracle for whether an incumbent exists, is complete, is physically feasible, and has proven optimality. A `TIME_LIMIT` incumbent may proceed to simulation/human review after independent feasibility validation, but it is never represented as optimal. This distinction is essential for bounded-runtime decision support on Windows where solver speed can vary by backend and machine.
